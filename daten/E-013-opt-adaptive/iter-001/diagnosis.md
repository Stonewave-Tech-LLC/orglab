The team treats the execute signal ('status set ✓') as proof that an item works. Nobody owns the job of confirming that items still work, and nothing records who has verified what. In both runs some items failed even though execute reported success (bounces), and some later reversed (P8 was overwritten when P15 was processed). The agent who found a failure often wasn't the owner. In seed 1003 a2 found P8 FAILED on the last tick but never told anyone, so a1 still reported P8 done. In the same run a3 sent the human a status list that was largely unverified. With full mesh, no board and only 4 tool calls per tick, coordination happens through broadcast messages that duplicate work (four agents inspecting P1 before it had been executed) instead of through shared state. As a result, about 3 false-dones per run pile up in the final ticks, when nobody has the time or the job of re-checking earlier results.
